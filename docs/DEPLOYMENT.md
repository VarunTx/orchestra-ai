# Deployment preparation

The supported and locally verified target is a private, single-host Docker Compose deployment. The `orchestra-ai` project name scopes its containers and persistent PostgreSQL volume. Start with `python3 scripts/setup_env.py` and `docker compose up -d --build --wait --wait-timeout 180`.

## Before hosting

1. Provision a Docker host and persistent disk; retain the PostgreSQL volume across releases. Do not use `down -v` unless intentional data deletion is authorized.
2. Generate new host-specific secrets. Keep `.env` readable only by the deployment operator. Inject provider credentials from your secret manager for a managed environment.
3. Keep engine, database and API private. Put a TLS reverse proxy in front of the web service. Set `APP_ORIGINS` on the web service to the exact external HTTPS origin (comma-separated if needed). Never use a wildcard.
4. Configure `COOKIE_SECURE=true` on the web service behind a TLS-terminating reverse proxy. Direct localhost development uses non-secure cookies. Add upstream identity/rate controls and replace the shared-token model before multi-user use.
5. Approve Gemini data handling/model/costs before setting `ENABLE_GEMINI=true`. The provider model can be changed through `GEMINI_MODEL`.
6. Run deterministic smoke and browser tests. Run crash-recovery checks only in a dedicated staging environment. Make a separate authorized live Gemini call to verify your provider account.
7. Back up PostgreSQL and verify restore on a separate database. Set your retention, capacity, TLS, monitoring and incident-response policies before production use.

## Rollout and rollback

- Back up the database before Conductor version changes. The pinned engine digest is the tested artifact; inspect upstream migration notes before changing it.
- Build images from a recorded commit. On a new host, run `docker compose up -d --build --wait --wait-timeout 180` and verify `docker compose ps`.
- Application containers run as non-root users. Engine/database images use their vendor defaults. This MVP does not implement HA or horizontal gateway/worker management.
- Roll back application images to a previous commit, preserving the database volume. Database schema migrations may require restoring a backup; do not assume that a binary downgrade is safe.
- `docker compose down` stops the project while retaining data. No public deployment is implied by the local setup.

## Render hosting

The repository includes `render.yaml` for a protected public dashboard, private FastAPI and Conductor services, Python workers, and private managed PostgreSQL. It uses the current Render plan identifiers and keeps automatic deployments off until the initial deployment is verified.

1. Connect the private GitHub repository to Render and select **New → Blueprint**.
2. Review the proposed four service instances and database cost. The Blueprint provisions paid resources; it is not a free-tier deployment.
3. Supply `GEMINI_API_KEY` through Render's secret field. Keep `ENABLE_GEMINI=false` until a provider test is authorized.
4. After deployment, copy `CONTROL_PLANE_TOKEN` from the private API service's environment into the dashboard sign-in form. It is generated by Render, not reused from the local machine.
5. The dashboard uses Render's runtime `RENDER_EXTERNAL_URL` for origin validation. For a custom domain, set `APP_ORIGINS` to its exact HTTPS origin. Cookies use the Secure flag.
6. Verify login, a diagnostic workflow, task inspection, and actual worker polls at the returned HTTPS URL. A successful local build does not prove hosted deployment success.

Cloud environment variables resolve private DNS and database credentials without hardcoding hosts. The worker group polls Conductor directly; the gateway and database are never exposed publicly by this Blueprint. The `.env` file and local test history are not uploaded to GitHub or imported into the hosted database.

Local volume migration: the renamed Compose stack uses `POSTGRES_VOLUME_NAME` from `.env` and `POSTGRES_VOLUME_EXTERNAL=true` to retain the original `conductor-control-plane_postgres_data` volume. New installations default to `orchestra-ai_postgres_data`.

References: [Render Blueprint specification](https://render.com/docs/blueprint-spec), [private services](https://render.com/docs/private-services), [current pricing](https://render.com/pricing). Hosted cost and provisioning remain pending account access and cost approval.

## Application database and owner login (added October 2026)

The API now creates its own `orchestra` database inside the existing PostgreSQL instance and runs SQL migrations at startup. Give the API service `DATABASE_HOST`/`POSTGRES_PASSWORD` access to the same server; do not point it at Conductor's schema.

Two additional secrets are required for a hosted deployment:

- `OWNER_PASSWORD` — dashboard password (stored only as a scrypt hash). Without it, only the master API token can sign in.
- `SECRET_KEY` — encrypts connector credentials at rest. Rotating it invalidates stored connector tokens.

The monitoring collector runs inside the API process; no extra service is needed. Keep `HTTP_CHECK_ALLOW_PRIVATE=false` outside local development and set `COOKIE_SECURE=true` only behind TLS. Railway service resources were not changed by this work.
